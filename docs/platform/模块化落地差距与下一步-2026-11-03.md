# 模块化落地差距与下一步（2026-11-03）

本文基于当前仓库代码盘点，配合《模块开发标准与平滑接入规范-v1.md》使用。它记录当前实现状态、不能直接删除的兼容点，以及建议的后续执行顺序。这里只做现状分析与开发拆分，不代表下述业务模块已完成。

## 当前结论

项目已经有可运行的外置模块加载链路和会员模块样例，但“模块目录信息”与“已安装可运行模块”仍由同一个 `ModuleRegistry` 表达。这个职责重叠是继续规模化添加模块前最先要拆解的问题。

不能直接删除静态模块描述符：企业必须在安装包之前就能看到已授权模块、启用企业授权、分配门店名额并进入安装中心；这些流程需要模块的名称、依赖、权限和操作元数据。与此同时，不能把目录元数据当成模块程序已经安装，否则菜单、权限组或接口可能显示成可用，但对应业务代码并不存在。

## 推荐执行顺序

### 第一步：拆分目录定义和运行时状态

**已完成第一阶段的运行边界：**总部模块列表在授权摘要上增加 `installed` 与 `installedVersion`；模块菜单接口只返回当前 `RuntimeState.loaded()` 中模块的菜单。静态 `ModuleRegistry` 仍保留在安装前管理链路中，确保未安装模块仍可查看授权、启用配置和名额分配。

外置模块业务 Handler 只由已加载 JAR 的显式配置注册；消费者及总部客户模块摘要 Provider 也检查运行时加载状态。总部安装中心和授权管理 API 不要求业务包已加载。平台商品目录不依赖客户实例运行时 Registry。

第一阶段验收已覆盖：已授权未安装时总部仍能管理模块授权且无业务菜单；真实外置模块仍能加载；会员消费者/总部详情 Provider 缺失时底座客户详情仍正常。完整测试结果记录在本次开发交接中，生产预览 API 需运行新打包版本才能看到新增状态字段。

**生命周期决策矩阵已补充：**`ModuleAccessQueryTest` 参数化覆盖有效授权、授权撤销、企业停用模块、门店分配撤销、离线只读、三日收尾期、收尾结束和授权未生效；每个场景同时检查读写结果，并确认模块业务数据行未被删除。`ModuleAccessGuardTest` 覆盖无员工权限时拒绝调用，`HqModuleControllerIntegrationTest` 覆盖未安装授权仍可管理但不返回业务菜单。验证结果：`care-core` 45 项通过；企业端相关回归 17 项通过；矩阵所在测试类 16 项通过。

### 第二步：把会员从旧固定路径收敛到外置模块

**前端路由收敛已完成：**模块导航只接受 `/modules/{moduleCode}` 命名空间内的服务端菜单；前端不再注册会员、机构、社区的旧固定路径。旧路径显示“页面不存在”，模块必须由实际加载的运行包提供入口。后端静态 descriptor 暂时保留，因为授权、依赖和安装前管理仍使用其目录元数据；不能将这部分误删为运行时入口。

当前无需为此重启或重构数据库。若既有部署曾将旧固定 URL 保存为书签，用户需要从工作台模块菜单重新进入。**静态 descriptor 与运行权限标签的耦合清理已完成：**安装前目录仍保留 moduleCode、名称、依赖和权限码，模块购买/授权/名额流程保持可用；菜单与资源操作只由实际加载包的 manifest 提供。未安装权限标签不再伪装成正式业务权限，既有已安装权限名称也不会因模块暂时卸载而被占位名称覆盖。验证覆盖 descriptor 目录边界、未安装总部管理和菜单隔离、外置模块启动注册。会员底座摘要继续使用现有可选 Provider，不向基础客户表增加会员字段。

### 第三步：确定并实现第一个新业务模块

机构和社区先分别完成产品边界、数据归属、岗位权限和迁移规格，再选一个范围较小且首发价值明确的业务开始。不要同时把两个空 POM 骨架扩成业务，以免共享底座 API 未定时产生交叉依赖。

实现必须包含模块规格、独立 manifest、thin JAR、模块自有迁移、HQ/STORE 页面和 API、模块权限标签、门店数据范围及升级/停用测试。若需会员信息，只调用会员公开 Provider/API；不要声明强制依赖，除非业务确认模块无法脱离会员独立工作。

### 第四步：移除无用骨架与静态注册

新包和接口稳定、授权预安装流程通过隔离集成测试、旧入口迁移完成后，再删除 tenant-app 中的旧描述符/静态标签及空 API/impl POM。删除前检查模块商品、企业授权、员工角色权限、预览数据库是否仍引用旧 `moduleCode`；稳定 `moduleCode` 不因实现迁移而改变。

## 第一阶段验收用例

1. 企业购买并取得机构模块正式授权，但没有下载或安装包：授权页面显示“已授权，待安装”，员工菜单不显示机构业务入口。
2. 包已安装但企业未启用：安装状态显示已安装，启用操作可见，业务 API 仍被拒绝。
3. 总部启用且给门店 A 分配名额：门店 A 的有权限员工可看到入口；门店 B 和无权限员工不可见也不可调用。
4. 门店 A 停用/撤店或名额撤回：新业务写入被拒，模块表和历史记录仍保留。
5. 模块未安装时访问客户列表/详情：页面只返回底座信息；可选模块详情缺失或超时不能阻断客户主数据。
6. 安装模块时迁移失败：计划进入恢复状态；不能通过删除模块表或自动回退代码假装成功。

## 当前建议

下一项代码工作是补充“已安装但企业未启用”“门店未分配”“授权过期/撤销”的端到端组合测试，确认总部和门店菜单、接口行为在各组合下完全一致。通过后，选择机构康养或社区居家中的一个，先确认业务边界、数据归属和会员依赖，再启动新模块实现。静态 descriptor 继续保留为授权目录元数据，直到目录定义与运行时 descriptor 在结构上完成独立建模。
