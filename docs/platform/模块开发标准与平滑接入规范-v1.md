# 模块开发标准与平滑接入规范 v1

本文是智慧养老项目新增、拆分和升级业务模块时的团队统一开发约定。目标是让基础系统在没有某个模块时仍可独立运行；安装模块只增加该模块自己的数据结构和运行能力；已有企业数据可以按明确规则接入，不要求重建企业数据库。

本文描述当前仓库的 `.caremod` v1、运行时 ABI v1 与现有底座 API。规范中的“必须”是代码评审要求；未来设想不视为当前能力。新增能力若超出当前 manifest、ABI 或宿主公开 API，先提出协议升级并做兼容设计，再实现模块。

## 1. 系统边界与术语

| 名称 | 含义 |
|---|---|
| 平台总端 | 项目团队运营的平台系统，管理企业登记、模块目录、授权、发布和更新。平台不持有企业自己的客户业务数据。 |
| 企业实例 | 客户自建部署的企业总部、门店工作区及用户端服务，共用该客户自己的数据库。企业负责自己的服务器、域名和微信配置。 |
| 底座 | 企业实例始终部署的组织、账号、客户、权限、授权校验、模块运行时等基础能力。它不属于可选业务模块。 |
| 模块 | 可独立签名、授权、安装、启停和升级的业务扩展。模块由稳定 `moduleCode` 标识，包含自己的后端、前端入口、权限声明和数据库迁移。 |
| 商品 | 平台用于售卖的单模块授权或套餐；商品 ID 与 `moduleCode` 是不同概念。 |
| 安装 / 启用 / 授权 | 安装表示程序和迁移已部署；启用表示企业实例允许模块运行；授权表示平台签发的有效许可。三者互不替代。 |

企业数据库按企业实例隔离。模块表无需再增加 `enterprise_id` 作为跨租户过滤条件，除非业务本身需要企业库内的多组织归属；门店数据则必须依据底座提供的数据范围上下文进行隔离。一个企业库内的模块数据不得被其他企业实例读取。

## 2. 模块接入生命周期

正常开通顺序如下：

1. 平台将模块包校验并发布；企业需拥有该模块的有效正式授权。
2. 企业总部在模块安装中心下载包并确认计划；客户侧执行器验证签名、底座版本、依赖和授权，先备份，再执行模块迁移。
3. 执行器完成重启和健康检查后，运行时才将包视为已安装并加载。计划确认或包下载成功本身不代表安装完成。
4. 企业总部启用模块。若模块有门店名额，先分配名额，再由对应门店启用；员工还需在权限组/角色中得到相应权限。
5. 服务端每次请求仍检查运行状态、授权、启用状态、员工权限及数据范围。隐藏菜单只是界面行为，不是访问控制。

模块未安装时：底座启动、登录、客户/门店基础功能必须正常；不得因缺少可选模块的表、Bean、路由或静态依赖而失败。移除运行包、授权到期、门店撤店、员工离职的语义不同，不能把其中任一状态等同于删除模块数据。

在当前企业端中，`ModuleRegistry` 提供模块描述符目录，支持安装前的授权、依赖和权限元数据解析；它包含目录定义不代表模块代码已安装。模块安装状态唯一依据是 `InstalledModulesRegistrar.RuntimeState.loaded()`：总部模块列表据此返回 `installed`/`installedVersion`，可用菜单只返回已加载模块；动态模块 Handler 和客户 Provider 也只在对应外置包实际加载后注册/聚合。新增代码不得仅用 `ModuleRegistry.contains(moduleCode)` 判断业务模块可运行。

## 3. 模块身份和规格登记

每个模块在开发前登记一份规格，至少填写以下字段：

| 字段 | 要求 |
|---|---|
| 中文名 / 英文名 | 中文名用于界面；英文名用于文档、代码评审和团队沟通。当前 manifest 只有 `module.name`，英文名写在模块 README/规格中。 |
| `moduleCode` | 稳定、全局唯一，小写字母开头，仅小写字母、数字和连字符，2 至 32 字符；一旦发布不可因改名而更换。当前正则为 `[a-z][a-z0-9-]{1,31}`。Java 包名将 `-` 替换为 `_`。 |
| 模块说明 / 业务边界 | 说明解决的问题、包含和不包含的功能、目标使用端及明确不承担的底座职责。 |
| 负责人 / 版本 | 指定模块维护人；模块版本采用数字点分版本。已发布版本不可覆盖或降级替换。 |
| 底座兼容范围 | 填写包含的 `minCoreVersion` 和不包含的 `maxCoreVersionExclusive`；只依赖已公开且有兼容承诺的 API。 |
| 依赖模块 | 填写 `moduleCode` 和最低版本；无依赖写空数组。不得依赖对方数据库表。发布前检查依赖存在、版本满足且无环。 |
| 端与入口 | 分别说明 HQ、STORE、CUSTOMER 是否提供入口。当前动态业务前端实际支持范围以《模块执行器与运行时接入》为准；不得把 manifest 声明误当成宿主已实现。 |
| 权限与数据范围 | 列出每项权限、用途、HQ/STORE 适用端、门店范围要求、写操作以及敏感信息等级。 |
| API | 统一使用 `/api/tenant/v1/modules/<moduleCode>/...`，逐项登记方法、路径、请求/响应、错误码、权限和幂等规则。 |
| 表与迁移 | 列出模块专属表名、外键、唯一约束、索引、数据保留和迁移版本；每个表归属唯一模块。 |
| 旧数据接入 | 写明匹配键、是否自动迁移、预览/确认流程、幂等键、审计信息和失败恢复方式。没有迁移时明确“只支持人工显式关联，不回填存量数据”。 |
| 测试 / 发布 / 回退 | 列出隔离数据库测试、越权测试、真实包冒烟、签名和发布步骤。说明哪些迁移不可逆及恢复依赖的安装前备份。 |

现有 manifest v1 对未知字段严格拒绝，禁止自行添加 `englishName`、租户初始化脚本等字段。中英文规格可先保存在 README/模块规格文件；如需成为机器可读 manifest 字段，必须先升级包协议、发布工具、验证器和兼容测试。

## 4. 代码与运行接口标准

### 4.1 目录与交付

模块源码放在 `backend/modules/<module-code>/`。独立维护 thin JAR、manifest 模板、`payload/migrations/`、前端入口与 README。最终 `.caremod` 是 ZIP，遵循《模块包规范 v1》；JAR 不得打入 Spring Boot、底座实现或其他模块实现，不得使用包扫描、`META-INF/services` 或自动配置文件发现模块 Bean。入口类通过 `ModuleEntrypoint` 显式返回本模块配置类。

模块 Java 类型仅放在 `com.smartelder.modules.<module-code替换连字符为下划线>` 命名空间中。模块不能新增 tenant-app 固定依赖；宿主通过已发布模块 API 和受校验的外置 JAR 加载模块。

### 4.2 API、权限和数据范围

- 所有管理 API 放在模块专属前缀下；每个 Handler 方法都声明 `@ModuleOperation(resource, operation)`，并在 manifest `resourceOperations` 中声明完全匹配的权限。
- 每个权限码格式为 `<moduleCode>:<resource>:<operation>`，并由 `ModuleEntrypoint.permissionNames()` 提供中文名称，准确覆盖 manifest 的权限集合。
- 写请求使用 POST/PUT/PATCH/DELETE，不允许 GET/HEAD/OPTIONS 改数据。响应沿用宿主统一响应封装；冲突返回 409、无权返回 403、输入错误返回 400、缺失资源返回 404。
- HQ 操作必须校验总部身份和相应权限。STORE 操作必须使用认证主体的门店范围；不得相信请求体或查询参数中的任意 `storePublicId` 来决定访问范围。
- 模块拦截器检查员工权限、授权与运行状态；服务层还必须校验业务不变量和资源归属。不能因 UI 隐藏按钮而省略服务端检查。
- 消费者接口必须由宿主认证当前客户，并将已认证客户稳定 ID 传给模块；禁止让客户端传任意 customer ID 后直接返回该客户资料。

依赖底座时使用 `care-core-api` 等公开 API，例如 `CustomerQueryApi`、`StaffAccessApi`；不要注入底座内部 Repository/实现类。模块间通信只能依赖明确版本化的公开 API/Provider，严禁跨模块 SQL、跨模块实体外键或读取对方数据库表。

现有可选扩展点包括：`CustomerFeatureProvider` 向消费者本人资料页增加只读模块摘要；`CustomerManagementFeatureProvider` 向有权限的总部客户详情增加模块摘要。Provider 必须属于对应模块包，声明模块代码和所需权限；宿主只在模块已加载、授权有效、已启用且访问者有权时聚合。一个可选 Provider 的异常不得使基础客户详情整体不可用。其他全局扩展点须先定义宿主 API 契约，不能通过反射猜测或共享数据库实现。

### 4.3 前端

菜单通过 manifest `menuEntries` 声明，权限码必须属于本模块。门店运行时页面入口按 ABI v1 制作单文件、自包含 ES module，默认导出 React 组件，使用宿主传入的 React、workspace、route、request；不能打包第二份 React，不能依赖相对 import 或额外运行时包。请求桥只允许本模块 API 前缀。HQ/CUSTOMER 动态业务入口是否可执行必须以宿主实现为准。

## 5. 数据库隔离、命名与迁移

1. 每个模块只创建自己的表，建议统一前缀 `<短模块码>_`；已发布模块不得未经迁移评审改变前缀。会员模块使用 `mem_` 前缀。
2. 模块迁移写入 `.caremod` 的 `migrations/V<递增序号>__<说明>.sql`。首次安装 baseline 为 0；迁移历史由 `flyway_module_<moduleCode>` 单独记录。
3. 发布后的旧迁移不可修改、删除或复用版本号。修复和结构演进必须追加迁移；包需保留完整迁移历史及原校验和。
4. 模块不得 `ALTER`、`DROP`、重命名底座表或其他模块表，不得把模块字段加到基础客户、门店、员工、订单表。业务需要扩展摘要时通过 Provider/API 提供。
5. 表的自增主键只用于本模块内部关系；跨模块/底座关系使用公开稳定 ID，并由所属服务验证目标存在及可见。不可把手机号、姓名、昵称等可变属性当关联键。
6. 对写入的关联数据加数据库唯一约束；并发敏感操作使用事务、行锁或版本号。关系创建/等级变更等重要业务必须同时写审计流水。
7. 删除、停用和授权到期默认保留业务数据。模块不提供无确认的级联清库；清理需企业管理员明确发起、审计、可撤销等待期（如适用）及独立备份策略。
8. 模块迁移失败且已开始执行后不能盲目将旧程序重新上线写库。按执行器规则进入恢复状态，并从安装前备份制定恢复；运行时不得自动删除表来“回滚”。

### 5.1 建表模板

以下为结构示意，不是可直接复用的客户表定义。按所用数据库补齐字段类型、索引与审计字段：

```sql
CREATE TABLE <prefix>_<entity> (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    public_id VARCHAR(36) NOT NULL UNIQUE,
    version BIGINT NOT NULL DEFAULT 0,
    created_at TIMESTAMP NOT NULL,
    updated_at TIMESTAMP NOT NULL
);
```

需要关联底座对象时，保存其公开稳定 ID，例如 `customer_public_id`，不复制其账号、手机号、认证信息或整行基础资料。读展示字段时经底座公开查询 API 获取，并按最小必要原则返回。

## 6. 平滑接入和兼容规则

### 6.1 新模块首次启用

- 安装前后底座表结构保持不变；模块新增自己的表、权限、菜单和 Provider。
- 未安装或未启用时，底座页面/API 不引用模块 Bean、表和路由；可选摘要缺失就返回空扩展列表，基础资料仍照常显示。
- 授权到期后执行读写策略由平台授权与企业数据保留规则共同决定。严禁因过期自动删表；具体模块应列出允许的历史查看、导出、写入和停用行为。
- 门店名额、门店启用与员工权限分别检查，不得把总部模块已启用视为所有门店员工都自动有权。

### 6.2 既有客户/门店接入

- 只通过底座的公开查询/服务接口选择既有对象，再保存稳定公开 ID。
- 用户/客户成为某业务身份（会员、签约对象、服务计划参与者等）必须由明确业务动作创建，不因安装模块就批量生成身份。
- 不按电话、姓名、身份证显示掩码或微信昵称自动合并账号。若确有业务需要导入，先做独立导入流程：预览匹配结果、显示冲突、人工确认、幂等执行、记录操作者和来源、导出失败行；重复执行不得重复创建关系。
- 不复制底座用户身份、密码、登录凭证或客户主档到模块表。只储存模块独有状态及必要的稳定外键。
- 历史业务需从外部系统导入时，定义源系统 ID 到本系统 public ID 的映射表、重复/冲突规则和回滚方案；导入过程不得静默覆盖现有资料。

### 6.3 模块版本升级

升级只能追加迁移，且要兼容已发布的数据。迁移步骤需说明锁、事务能力、预计时间、备份、幂等性和失败恢复。大规模转换优先采用“新增字段/表 → 双读或回填 → 校验 → 切换 → 后续版本清理旧结构”的扩展迁移，不能一次升级删除旧字段后才发现旧版代码仍依赖它。

## 7. 会员模块实例：旧客户平滑成为会员

会员模块规格：中文名“会员等级管理”，英文名“Membership Management”，稳定代码 `membership`。英文名目前只登记在本规范和模块 README；manifest v1 的显示名保持 `name: 会员管理`。当前兼容范围为底座 `[2.1.0, 3.0.0)`，无模块依赖。

### 7.1 安装前后数据

安装前，企业只有底座客户账号/客户资料；没有会员表，也没有“所有客户默认是会员”的标记。客户仍可正常登录、浏览企业/门店首页以及使用底座已提供的功能。

安装会员包后，模块迁移只新增 `mem_level`、`mem_member`、`mem_change` 三张表，不修改底座客户表。关键约束如下：

| 表 | 用途 | 关键关联/约束 |
|---|---|---|
| `mem_level` | 企业自定义等级和权益说明 | `public_id` 唯一；等级名唯一；停用用 `enabled=false`，不删除被引用等级。 |
| `mem_member` | 客户成为会员后的模块身份 | `customer_public_id` 唯一，关联底座稳定客户 ID；同一企业客户最多一个会员档案。 |
| `mem_change` | 开通和等级变化审计 | 记录会员、变更前后等级、原因、操作人和时间。 |

底座客户 API 当前定义为 `CustomerQueryApi.find(String)`、`search(String, int)`，返回最小摘要 `CustomerSummary(publicId, username, displayName)`。模块不查询底座客户表。

### 7.2 业务接入流程

1. 总部安装并启用会员模块，创建会员等级及权益说明。
2. 总部在会员页面搜索已经存在的客户；搜索结果来自底座客户查询 API。
3. 管理员核对客户后，明确选择“开通会员”及初始等级、原因。后端检查客户真实存在、等级可用、总部身份和 `membership:member:write` 权限。
4. 模块以客户 `publicId` 写入 `mem_member`，唯一约束防止重复；同一事务写入 `mem_change`。并发重复请求按冲突返回，不产生第二份会员或漏记流水。
5. 后续改级使用版本号/行锁校验并在同一事务追加流水；等级停用后已有会员仍可查看原等级状态，但不能再将新会员分配到停用等级。
6. 消费者的会员摘要由底座认证其本人，再由 `CustomerFeatureProvider` 返回；总部客户详情使用受数据可见范围和 `membership:member:read` 权限保护的 `CustomerManagementFeatureProvider`。门店不获得客户全集，当前交互要求客户主动出示客户编号，门店员工再调用查询并只获得最小会员身份信息。当前 API 接收客户公开编号并以员工权限拦截，尚没有短时码/签名凭证来技术验证编号是否由客户本人现场出示；若产品要求强制证明客户同意，必须另行设计有时效、防重放的客户凭证流程，不能把当前员工权限检查描述为客户授权证明。

因此，从“没有会员模块”到“启用会员”无需重建数据库、给客户账号增加全局标记或自动改造所有旧客户。只有被总部明确开通的客户才产生会员关系。移除菜单、模块暂停或授权状态变化也不会删除 `mem_member` 和 `mem_change` 数据。

当前权限包括 `membership:level:read/write`、`membership:member:read/write`、`membership:history:read` 和门店 `membership:identity:read`。接口前缀为 `/api/tenant/v1/modules/membership`。完整响应与构建方式以 `docs/platform/会员模块使用说明.md` 和模块源码为准。

## 9. 机构康养和社区居家迁移清单

以下为把现有占位或早期实现整理成独立模块前的迁移任务。逐项评估后再排期，本规范本身不代表这些业务已经实现。

### 9.1 机构康养模块

- [ ] 定义模块规格、英文名、稳定代码、模块边界和首版业务流程；识别入住管理、床位、护理计划等是否确属该模块。
- [ ] 盘点现有底座中可能相关的客户、组织、员工、预约或服务数据；不得直接移动/重命名底座表，先明确模块专有实体和稳定 public ID 关联。
- [ ] 设计机构/区域/床位等模块表及唯一约束；确定数据属于总部还是门店，门店读写按 StaffAccess/data-scope API 实施。
- [ ] 将每个总部、门店页面/API 的权限加入模块 manifest 与 `permissionNames`；操作 Handler 加 `@ModuleOperation`，测试 HQ/STORE 越权及跨门店拒绝。
- [ ] 如从旧底座数据接入，建立显式映射和预览确认流程；证明重跑幂等、冲突不会覆盖、失败可审计恢复。
- [ ] 为模块安装前后、停用、授权过期、门店撤店和升级准备数据保留/查看/导出策略；不得自动清理机构业务数据。
- [ ] 独立编译 thin JAR、添加完整迁移历史和受支持端入口；使用隔离数据库测试真实 `.caremod` 安装和错误恢复。

### 9.2 社区居家模块

- [ ] 定义社区网格/服务范围、上门服务、服务人员与预约/工单之间的边界；会员、支付等能力作为明确依赖或公开 API，不复制其数据表。
- [ ] 盘点当前客户、门店、服务预约等底座数据；确认哪些是基础主档，哪些才是社区居家专属状态。不得在底座客户表塞入社区服务字段。
- [ ] 模块自有表按稳定 public ID 关联客户、门店和员工；验证服务记录的数据范围与执行门店一致。
- [ ] 明确总部派单、门店处理、客户查看各自的角色、权限和状态机；所有状态转换服务端校验并记录操作流水。
- [ ] 需要兼容既有预约或订单时，制定一对一映射、重复检测、客户/门店归属核验和失败报告；不能靠手机号推断归属。
- [ ] 声明所依赖模块的最低版本，只经受支持接口调用；增加依赖缺失、版本过低、授权到期和门店无名额测试。
- [ ] 完成独立迁移、停用与授权到期数据策略、门店范围测试和包安装冒烟，确认基础客户页面在模块未安装时不受影响。

## 10. 发布前评审门槛

- [ ] 模块规格填写完整，`moduleCode` 和权限稳定且无命名冲突。
- [ ] 包只有模块自己的 thin JAR、前端文件和按序迁移；manifest 的 files 摘要完整，签名来自受信发布密钥。
- [ ] 无底座/其他模块表的 DDL、SQL、Repository 访问或跨模块实体外键。
- [ ] 所有写 API 有权限、授权、启用状态、数据范围、输入校验和并发约束测试。
- [ ] 旧客户关联遵循显式动作和稳定公开 ID；没有按电话自动合并或默认全量开通。
- [ ] 分别验证未安装、已安装未启用、已启用、无员工权限、门店未分配、授权到期与迁移失败状态。
- [ ] 在隔离企业库完成真实签名包冒烟；生产更新前明确客户侧备份、执行器和人工恢复方案。
