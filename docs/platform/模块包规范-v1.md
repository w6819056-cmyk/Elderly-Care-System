# 模块包规范 v1

## 当前范围

本规范面向模块发布包的静态校验。静态验证成功不表示获得授权、不表示已安装，也不执行任何 Java、JavaScript 或 SQL。安装运行链路见实施计划的后续阶段。

## 文件格式

后缀 `.caremod`，内容为 ZIP。根目录只有 `manifest.json`、`manifest.sig` 和 manifest 声明的文件，允许无内容的目录项。

```text
membership-1.0.0.caremod
├── manifest.json
├── manifest.sig
├── backend/module.jar
├── frontend/hq.js
├── frontend/store.js
├── frontend/customer.js
└── migrations/V1__membership.sql
```

manifest.json 是 UTF-8 JSON，含 formatVersion=1、keyId、module（沿用 ModuleDescriptor 全部字段）、minCoreVersion、maxCoreVersionExclusive、entryClass、frontendEntries（HQ/STORE/CUSTOMER 到文件路径的映射）、migrations（顺序路径列表）、files（相对路径到小写 SHA-256 的映射）。全部入口及迁移必须包含于 files。backend/module.jar 为约定必需项。协议版本 v1 使用 3 段纯数字版本，不含预发布后缀；平台原版本目录支持更多版本形式，上传安装包时按此更严格规则校验，不修改原数据。

module.code 是唯一模块代码，module.version 是包版本。权限必须以自身 module.code + 冒号开头；支持权限中文名称由后续安装注册契约携带，不能在插件内自行创建跨模块权限。依赖按现有 ModuleDependency 声明，不能依赖自身、重复依赖，安装器额外检查循环依赖与正式授权。

minCoreVersion 包含，maxCoreVersionExclusive 不包含。首次发布包不允许借依赖程序版本满足正式授权条件。

## 签名与校验

发布工具计算每个 payload 文件的 SHA-256，生成 manifest 原始字节，再用受信发布私钥以 Ed25519 签名。manifest.sig 为 Base64 ASCII；签名覆盖 manifest.json 的原始字节，修改空格或字段顺序也需要重新签名。

平台和企业使用各自配置的可信 keyId→公钥映射。keyId 仅用于选择公钥，不允许使用包内公钥作为信任来源；未知 keyId、错误签名均拒绝。发布包签名密钥与软件销售授权签名密钥用途分离。

验证器拒绝绝对路径、盘符、反斜杠、点段、重复条目、未声明文件或缺失文件、错误摘要、未知 JSON 字段和重复 JSON 字段。压缩文件最大 64MiB，展开总量最大 64MiB，单文件最大 32MiB，最多 256 个条目，manifest 最大 256KiB，签名最大 1KiB。大包需未来协议或显式受控配置扩展，不默默放开限制。

返回值只表示包通过静态验证。解压器仍须在私有 staging 目录用规范化路径校验落点，不能执行符号链接或包内安装脚本。包不能自行启动外部进程。JAR 入口的接口兼容性、前端 ABI、SQL 版本顺序、迁移历史校验由安装阶段检查；静态 ZIP 检查不能替代这些步骤。

## 状态与运行原则

发布：UPLOADED → VERIFIED → PUBLISHED；未发布不可交付，版本发布后不可覆盖。

安装：DOWNLOADED → VERIFIED → AWAITING_CONFIRMATION → INSTALLING → RESTART_PENDING → ACTIVE；失败到 FAILED 或 RECOVERY_REQUIRED。状态由后续安装器持久化，当前校验库不伪造安装成功。

模块更新涉及数据库时先备份。数据库迁移后的失败不保证可自动降级。程序已安装、企业已授权、门店已分配名额、门店已启用、员工有权限分别检查。
