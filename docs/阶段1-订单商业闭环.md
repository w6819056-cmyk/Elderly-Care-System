## 1. 范围与结论

本阶段已完成以下能力：

1. 平台创建套餐，并维护套餐内模块、周期、门店名额和最低成交价。
2. 企业按套餐或模块直购方式询价。
3. 已正式授权模块在套餐购买时按标准价抵扣。
4. 活跃周期授权续费时从原到期日继续叠加，而不是从付款日重新计算。
5. 必需依赖校验，支持在同一订单中补齐依赖，或使用企业已有的正式授权。
6. 创建订单并保存不可变的模块名称、价格、周期、名额等订单快照。
7. 使用 `Idempotency-Key` 保证订单创建的幂等性。
8. `MOCK` 渠道模拟支付。
9. 已支付订单全额模拟退款。
10. 订单状态流转白名单和平台审计记录。

本阶段**未完成**以下能力，不得在对外说明中写成已完成：

- 支付成功后的自动履约。
- 写入或续期 `pf_entitlement`。
- 生成 Ed25519 许可证。
- 微信支付、支付宝、银联真实渠道接入。

## 2. 编码与核心术语

### 2.1 模块编码与套餐编码不是同一种规则

模块编码用于 `pf_module_definition.code`、价格、依赖、订单项和前端菜单标识：

```regex
^[a-z][a-z0-9-]{1,31}$
```

- 小写字母开头。
- 只允许小写字母、数字和连字符 `-`。
- 长度 2～32。
- 示例：`institution-care`、`community-home`、`membership`。

套餐编码用于 `pf_plan.code`，是另一套规则：

```regex
^[a-z][a-z0-9_]{0,39}$
```

- 只允许下划线 `_`，不允许连字符 `-`。
- 示例：`elderly_basic_suite`。

开发时不能把两套正则混用，也不能把套餐编码当作模块编码传给订单接口。

### 2.2 企业标识

订单接口中的 `enterpriseId` 是企业对外公开 ID，例如 `ent_...`，不是数据库自增主键。服务内部会先解析为 `pf_enterprise.id` 后再用于订单、授权等关联。

### 2.3 授权类型

当前依赖判断只把以下授权视为“正式有效授权”：

```text
license_type = FORMAL
status = ACTIVE
starts_at <= now
perpetual = true OR expires_at > now
```

因此：

- `TRIAL` 不能满足付费模块的必需依赖。
- `PLATFORM_GRANT` 当前也不能满足付费模块依赖。
- 过期、未开始、非 `ACTIVE` 的正式授权不满足依赖。
- `OPTIONAL` 依赖不参与购买阻断，只表达运行期可选能力。

## 3. 模块接入结构与调用边界

### 3.1 分层结构

```text
platform-app
  只暴露平台控制面 HTTP API，不加载企业业务模块实现。

platform-core
  平台身份、企业、实例、模块目录、价格、套餐、订单、支付、退款和审计。

platform-licensing
  Ed25519 授权文档的签名与验签契约，不保存企业业务数据。

care-module-api
  所有业务模块共享的模块描述、依赖和权限码契约。

care-business-api
  面向业务模块的稳定公共业务契约。

modules/<module>-api
  模块对外接口、DTO、事件契约。

modules/<module>-impl
  模块内部实现、Entity、Mapper 和数据库访问。
```

### 3.2 模块描述符的真实结构

`ModuleDescriptor` 当前字段为：

```java
record ModuleDescriptor(
    String code,
    String name,
    String version,
    int menuOrder,
    List<ModuleDependency> dependencies,
    Set<String> permissionCodes
)
```

`ModuleDependency` 当前字段为：

```java
record ModuleDependency(String moduleCode, String minimumVersion)
```

上述两个类位于：

- `E:\yanglao\backend\libs\care-module-api\src\main\java\com\smartelder\module\api\ModuleDescriptor.java`
- `E:\yanglao\backend\libs\care-module-api\src\main\java\com\smartelder\module\api\ModuleDependency.java`

注意：依赖描述符中没有 `dependencyType` 字段。平台目录表 `pf_module_dependency` 额外保存 `dependency_type`，取值为 `REQUIRED` 或 `OPTIONAL`。

### 3.3 描述符与平台目录的关系

平台目录是运行时权威目录；`ModuleDescriptor` 是代码侧契约。两者需要共同维护并保持一致的内容包括：

- 模块编码。
- 模块版本。
- 菜单顺序。
- 依赖模块及最低版本。
- 权限码。

平台目录额外维护：

- 依赖类型 `REQUIRED` / `OPTIONAL`。
- 售价、币种、周期、门店名额。
- 试用配置。
- 上下架状态。

新模块上线时必须同时完成代码描述符和平台目录登记，不能只在其中一处增加模块。依赖循环由平台目录保存时统一检查。

### 3.4 新模块开发规则

1. 新模块必须依赖 `care-module-api`。
2. 模块之间只能通过公开 API 或领域事件交互。
3. 禁止访问其他模块的 Entity、Mapper 和数据库表。
4. 禁止跨模块直接写 SQL 或建立跨模块数据库外键。
5. 模块只操作自己的表，并保留自己的 Flyway 迁移文件。
6. 新模块只能新增迁移文件，不能修改已经发布的迁移文件。
7. 模块依赖其他模块时，保存对方的稳定 `public_id` 或契约 DTO，不复制对方内部主键作为跨模块耦合点。
8. 模块依赖基础底座时，依赖 `care-core-api` / `care-business-api` 的稳定接口，而不是直接依赖底座实现类。
9. 前端菜单是否显示由服务端返回的“已授权模块 + 菜单顺序”决定，不能把前端隐藏当作安全控制。
10. 每个受控接口仍必须由服务端校验企业授权、门店名额和角色权限。

推荐的新模块目录：

```text
backend/modules/<module-code>/
  <module-code>-api/
  <module-code>-impl/
```

### 3.5 模块数据演进示例

假设先上线模块 A，后上线依赖 A 的模块 B：

```text
A 已发布：A 自己的表、迁移、公开 API、事件。
B 新增：B 自己的迁移和表。
B 的依赖：ModuleDependency("module-a", "1.2.0")。
B 调用 A：通过 A 的公开 API，或订阅 A 的领域事件。
B 不调用：A Entity、A Mapper、A 的内部表。
```

如果 B 还需要 A 增加字段或行为，应由 A 新增自己的迁移和 API 版本，再由 B 声明最低版本。当前 Task 6 会保存最低版本，但**尚未实际比较**企业已授权版本是否达到最低版本；这一点必须在 Task 7 或后续版本治理任务中补齐。

### 3.6 平台库与企业业务库边界

平台控制库只能保存平台控制面数据：

- 平台账号、角色、权限。
- 企业主体、部署实例、激活码。
- 模块目录、版本、依赖、价格、套餐。
- 平台销售订单、平台收款、退款、授权、许可证和心跳。
- 平台审计、幂等和 outbox 事件。

平台控制库不得保存：

- 企业客户、老人、家属。
- 门店员工。
- 企业业务订单。
- 企业支付流水。
- 健康数据。
- 企业小程序 `openid` 或其他客户身份数据。

企业业务数据必须进入企业自己的业务库或独立 Schema。平台端不能通过跨库查询获得企业业务明细。

## 4. 接口清单

所有接口都在平台控制面，统一返回：

```json
{
  "code": "OK",
  "message": "成功",
  "data": {},
  "traceId": "...",
  "timestamp": "..."
}
```

| 方法 | 路径 | 权限 | 成功状态 | 用途 |
| --- | --- | --- | --- | --- |
| `POST` | `/api/platform/v1/plans` | `platform.plan.manage` | `201` | 创建在售套餐 |
| `GET` | `/api/platform/v1/plans?enterpriseId=...` | `platform.plan.view` | `200` | 查询企业可见套餐 |
| `POST` | `/api/platform/v1/orders/quote` | `platform.order.view` | `200` | 询价，不落订单 |
| `POST` | `/api/platform/v1/orders` | `platform.order.manage` | `201` | 创建订单，必须带幂等键 |
| `GET` | `/api/platform/v1/orders/{publicId}` | `platform.order.view` | `200` | 查询订单详情 |
| `POST` | `/api/platform/v1/orders/{publicId}/pay-simulated` | `platform.order.manage` | `200` | 模拟支付 |
| `POST` | `/api/platform/v1/orders/{publicId}/refund` | `platform.order.manage` | `200` | 全额模拟退款 |

`POST /orders` 必须带：

```http
Idempotency-Key: <最大 100 字符的唯一键>
```

金额全部使用 `BigDecimal`，数据库为 `DECIMAL(12,2)`，JSON 输出为字符串，例如 `"650.00"`。不得使用浮点数计算金额。

## 6. 报价、抵扣与续费规则

### 6.1 请求模式二选一

- 套餐模式：`planCode` 非空，`items` 必须为空，不能传 `period`。
- 直购模式：`items` 非空，必须传 `period`，不能传 `planCode`。

不满足时返回 `INVALID_REQUEST / 400`。

### 6.2 模块与价格校验

- 同一订单不能包含重复模块。
- 模块必须存在且为 `ON_SALE`。
- 模块价格方案必须存在且为 `ON_SALE`。
- `billingMode` 只能是 `PERIOD` 或 `PERPETUAL`。
- `PERIOD` 的 `durationDays` 必须大于 0。
- `PERPETUAL` 的 `durationDays` 必须为 0。
- `storeQuota` 必须大于 0，并且与价格方案完全一致。
- 同一订单内所有模块币种必须一致。
- 已永久正式授权的模块不能再次直购，返回 `MODULE_ALREADY_PERPETUAL / 422`。

### 6.3 周期续费

对同一企业、同一模块已有活跃正式周期授权时：

```text
新的到期时间 = 当前 expires_at + durationDays
```

不是从付款日计算。已过期授权则从当前时间重新计算。

### 6.4 套餐抵扣

套餐对“已有正式有效授权”的模块按标准价抵扣：

```text
最大抵扣额 = 套餐金额 - 套餐最低成交价
实际抵扣额 = min(已有正式授权模块标准价合计, 最大抵扣额)
应付金额 = 套餐金额 - 实际抵扣额
```

抵扣后的金额按未拥有模块的标准价比例分摊；使用分为单位的最大余数法，保证分摊结果精确到 2 位小数且总额不丢失 1 分钱。

套餐内已有正式授权的模块：

- `actualAmount = 0.00`
- `entitlementEffect = false`
- 订单项标记 `SKIPPED_EXISTING`
- 保留原到期时间，不重复延长

套餐内未拥有的模块会生成授权效果，订单项标记 `PENDING`。

套餐列表隐藏条件严格为：**套餐内每个模块都已永久拥有**。只有周期授权不会导致套餐隐藏；周期到期后仍可再次购买或续费。

### 6.5 套餐报价的已拥有判断

套餐报价使用“正式有效授权”判断模块是否已有：

- 未过期周期正式授权算已拥有。
- 永久正式授权算已拥有。
- `TRIAL` 和 `PLATFORM_GRANT` 不使套餐隐藏，也不按正式授权抵扣。
- 如果套餐内全部模块都已正式授权，报价返回 `PLAN_ALREADY_OWNED / 422`。

## 7. 必需依赖校验

### 7.1 判定规则

模块的 `REQUIRED` 依赖满足以下任一条件即可：

1. 同一订单中已包含该依赖模块。
2. 企业已有该依赖模块的正式有效授权。

依赖校验只检查 `REQUIRED`；`OPTIONAL` 不影响下单和启用。

### 7.2 失败原子性

依赖或价格校验在订单落库前执行。失败时：

- 不创建 `pf_subscription_order`。
- 不创建 `pf_subscription_order_item`。
- 不留下幂等记录。
- 返回 `MODULE_DEPENDENCY_MISSING / 422` 或对应价格、套餐错误。

### 7.3 已知边界

当前 `minimumVersion` 会被模块目录保存，但订单依赖校验只确认“模块存在且已正式授权”，**没有比较企业实际授权版本是否大于等于 `minimumVersion`**。模块版本治理在 Task 7 或后续版本中补齐。

## 8. 幂等规则

### 8.1 订单创建幂等

适用范围：`POST /api/platform/v1/orders`。

- 相同幂等键 + 相同请求体：返回首次创建成功的订单，不重复创建。
- 相同幂等键 + 不同请求体：返回 `IDEMPOTENCY_CONFLICT / 409`。
- 相同幂等键 + 不同方法或路径：返回 `IDEMPOTENCY_CONFLICT / 409`。
- 缺少幂等键：返回 `INVALID_REQUEST / 400`。
- 订单创建失败时事务回滚，首次请求失败后可以用同一键重新尝试正确请求。
- 幂等记录保留 30 天。
- `request_hash` 针对原始请求体计算，不要在上游重新序列化后再传入不同字节的请求体。

### 8.2 支付和退款边界

- 模拟支付通过 `channelTransactionNo` 去重：同一订单和同一渠道交易号重复调用，返回已有订单结果。
- 同一渠道交易号被不同订单使用，返回 `CONFLICT / 409`。
- 已支付订单使用新的渠道交易号再次支付，返回 `ORDER_STATE_CONFLICT / 409`。
- 退款当前未使用 `Idempotency-Key`；重复退款会因状态机返回 `ORDER_STATE_CONFLICT / 409`。
- 如果后续需要支付、退款也支持通用幂等，应复用 `IdempotencyService`，而不是另写一套幂等表。

## 9. 订单状态机、支付与退款

### 9.1 状态白名单

```text
DRAFT -> PENDING_PAYMENT
PENDING_PAYMENT -> PAID / PAYMENT_FAILED / CANCELLED
PAID -> FULFILLING / MANUAL_REVIEW / REFUND_PENDING
FULFILLING -> FULFILLED / MANUAL_REVIEW
FULFILLED -> REFUND_PENDING
REFUND_PENDING -> REFUNDED
```

所有非法流转抛 `ORDER_STATE_CONFLICT / 409`，并且必须在事务中避免部分写入。

注意：

- 创建订单时直接写入 `PENDING_PAYMENT`，当前没有对外提供 `DRAFT` 创建接口。
- Task 6 支付成功后停在 `PAID`，不自动进入 `FULFILLING` 或 `FULFILLED`。
- 退款当前直接从 `PAID` 或 `FULFILLED` 进入 `REFUND_PENDING`，再立即进入 `REFUNDED`。
- 未支付订单退款返回 `ORDER_STATE_CONFLICT / 409`，不能生成退款记录。

### 9.2 审计动作

当前写入：

```text
ORDER_CREATED
ORDER_PAID_SIMULATED
ORDER_REFUNDED
```

审计目标是 `SUBSCRIPTION_ORDER`，目标公开 ID 是订单 `publicId`。Task 7 的履约和授权动作应继续使用 `PlatformAuditService` 写入独立动作，不得修改既有审计记录。

## 11. 小组成员接入指引

### 11.1 新增模块的最小步骤

1. 在 `backend/modules/` 下创建 `<module>-api` 和 `<module>-impl`。
2. 在 `api` 模块定义公开 DTO、接口和事件。
3. 在 `impl` 模块编写业务实现、自己的 Entity、Mapper、迁移和测试。
4. 引入 `care-module-api`，实现并注册 `ModuleDescriptor`。
5. 只通过 `care-business-api` 或其他模块的 `*-api` 调用外部能力。
6. 在平台目录创建模块，登记编码、名称、菜单顺序、版本、依赖、权限码。
7. 为模块配置在售价格和门店名额，完成上下架。
8. 为 `REQUIRED` 依赖准备同订单补齐或正式授权路径。
9. 编写“无授权不可用、门店名额不足不可用、依赖缺失不可下单”的成功和失败测试。
10. 更新模块说明、菜单顺序、权限码和迁移说明。

### 11.2 模块之间的调用约定

推荐调用：

```text
业务模块 -> 对方 *-api 接口 / DTO
业务模块 -> 领域事件
业务模块 -> care-business-api 基础能力
```

禁止调用：

```text
业务模块 -> 对方 Entity / Mapper
业务模块 -> 对方数据库表
业务模块 -> 平台控制库 pf_* 业务表
platform-app -> 企业业务模块实现
企业业务模块 -> platform-core 内部实现
```

如果两个模块需要保持事务一致性，优先发布领域事件并使用 outbox；不要让 B 模块直接打开 A 模块的数据库连接。

### 11.3 前端模块菜单

后端返回的菜单顺序来自平台目录 `menu_order`，前端只负责渲染。建议接口返回结构包含：

```json
{
  "moduleCode": "institution-care",
  "name": "机构康养",
  "menuOrder": 20,
  "enabled": true,
  "licenseStatus": "ACTIVE",
  "entry": "/institution"
}
```

前端过滤 `enabled=false` 的入口只是减少误操作，真正的授权校验必须在业务接口上执行。模块依赖、门店名额、企业状态和角色权限都不能只依赖前端隐藏。

## 13. 已知边界与 Task 7 交接

Task 6 结束后，订单只到 `PAID`：

```text
PENDING_PAYMENT -> PAID
```

Task 7 需要新增：

- `EntitlementService.applyPaidOrder(long orderId)`：读取已支付订单，幂等地生成或续期 `pf_entitlement`。
- 永久授权和周期授权的差异处理。
- 订单项 `SKIPPED_EXISTING` 的跳过处理。
- 套餐/直购订单的正式授权写入。
- `LicenseIssueService.issueForInstance(...)`：生成 Ed25519 签名许可证。
- 履约失败进入 `MANUAL_REVIEW` 或可重试状态。
- 授权版本、最低依赖版本和心跳校验。
- 真实支付和退款的渠道适配器。
- 确认退款后的授权回收/失效策略。

在这些能力完成前，不应把“支付成功”解释为“模块已经可以使用”，也不应向企业开放依赖该订单的授权。
