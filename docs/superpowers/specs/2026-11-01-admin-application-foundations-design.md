# 平台与企业管理端应用底架设计

- 日期：2026-11-01
- 状态：设计已获用户确认，待文档审阅
- 项目：模块化多企业养老 SaaS
- 相关路线图：[模块化多企业养老 SaaS 实施路线图](../plans/2026-10-30-modular-saas-delivery-roadmap.md)

## 1. 目标与范围

为平台运营人员与企业员工提供两个独立构建、独立发布、部署位置也不同的浏览器管理应用：

1. **平台总管理端**：由我们部署并运行在平台方服务器，平台管理员登录后进入平台工作区，按平台权限展示导航并访问受保护路由。
2. **企业总部/门店工作台**：由客户部署并运行在客户企业总部服务器。总部员工和门店员工使用同一应用及租户员工认证；根据员工类型、角色权限和数据范围确定默认工作区、导航和可访问路由。该企业后端和企业数据库属于客户自有部署。

本次交付的是可扩展应用底架：独立入口、登录/退出、会话恢复、受保护路由、权限导航、API 客户端、无权限/会话过期/加载失败状态、基础布局，以及少量已有 API 能支撑的页面。它不代表平台运营或企业经营功能已全部完成。

用户客户端作为后续独立子项目处理，包括品牌小程序和统一域名下的品牌网站；预期流程为平台公开首页、选择企业品牌、品牌首页、选择门店、门店首页。当前子项目不改造旧小程序，也不创建该流程的假数据页面。

## 2. 现状与约束

- 当前 `admin/` 是 React 18、TypeScript、Vite 单应用，承载旧版业务页面，并新增了 `/hq/login` 与 `/hq/modules`。
- 平台后端提供 `POST /api/platform/v1/auth/login`、`GET /api/platform/v1/auth/me`；平台登录成功响应含 access token、过期时间和 `PlatformPrincipal`，其中包含角色码和权限码。
- 租户后端提供 `POST /api/tenant/v1/auth/login`、`GET /api/tenant/v1/auth/me`。`TenantStaffPrincipal` 包含 `staffType`、`homeStoreId` 和服务端解析的权限/数据范围。
- 租户菜单接口为 `GET /api/tenant/v1/modules/menus`；总部/门店组织、员工 IAM 和模块授权 API 已存在，但对应管理页面尚不完整。
- 平台 API 默认端口为 `8081`，租户 API 为 `8082`。
- 生产部署中，平台前端和平台后端部署在我们控制的平台基础设施；企业租户前端、租户后端和企业业务数据库由客户部署在其总部服务器/基础设施。开发端口只是本地开发默认值，不代表生产拓扑。
- 企业客户端浏览器访问客户部署的租户工作台/API；租户后端按授权协议主动向平台服务发起出站通信。平台总管理端不代理、不查询、不存储企业客户、员工、订单、支付、健康等租户业务数据。
- 企业端基础设施、企业域名/证书、微信小程序配置及其客户数据由客户持有和配置；平台只提供产品、授权控制面及约定的授权校验服务。
- 平台令牌与租户员工令牌必须由不同应用客户端、不同存储键和不同 API 请求层管理；两种会话不得互相恢复、附带或清理。
- 服务端始终是权限最终判定方。前端权限检查只控制导航和路由体验，不能替代 API 授权。

## 3. 方案与决策

考虑过以下实现边界：

| 方案 | 优点 | 代价 |
| --- | --- | --- |
| 平台与企业后台在同一 SPA 以路径隔离 | 复用依赖和页面组件，初期工作量小 | 发布、会话和 API 配置仍共处一个前端应用，边界容易被误用 |
| 平台控制台与租户工作台独立构建；总部和门店共用租户工作台 | 与两套身份/权限域对应，部署与会话边界清楚；总部和门店复用租户员工登录与公共组件 | 需要维护两个构建入口及各自运行配置 |
| 平台、总部、门店分别构建 | 部署颗粒更细 | 总部/门店共用的租户认证与能力会重复，当前没有足够需求支撑三套应用 |

采用第二种方案。第一批管理端交付为平台总管理端和企业租户工作台；二者独立构建并分别部署在平台方与客户总部。品牌客户端后续单独设计。采用同一仓库中的独立前端应用目录和独立 Vite 构建配置，现有 `admin/` 保留为旧版兼容应用，不在本次删除或迁移其旧页面。

## 4. 应用结构

新增两个应用根目录（实现计划阶段确定与现有构建脚本一致的命名与命令）：

```text
admin-platform/      平台控制台，调用 platform-app
admin-tenant/        企业租户工作台，调用 tenant-app
admin/               现有旧管理端，暂时保持可构建和运行
miniprogram/         现有小程序，后续品牌客户端项目再演进
```

平台控制台和租户工作台可复用构建工具及 UI 依赖版本，但本轮不建立复杂共享组件包。只有确有重复且边界稳定的纯 UI 组件才考虑后续抽取；登录、存储和 API 客户端不得共享。

### 平台控制台

- 未认证访问受保护路由时跳转平台登录页。
- 登录调用平台登录 API；应用初始化/刷新时调用 `/me` 验证现存会话，服务端拒绝后清除本应用会话并返回登录页。
- 根据 `permissionCodes` 过滤平台导航和本地受保护路由。导航项必须映射到平台后端已经存在的权限码。
- 先接通平台身份/首页壳，以及现有企业、实例/授权、模块目录、套餐、销售订单、平台账号/角色等 API 能支撑的入口。没有可用页面/API 的菜单不作为已完成业务功能展示。
- 业务页面以独立阶段接入；本底架可提供明确的空工作区组件和错误/加载状态，但不得显示虚构统计数字。

### 企业租户工作台

- 总部和门店使用相同的租户员工登录 API 和员工会话；登录后按 `staffType` 进入 `/hq` 或 `/store` 工作区。
- `/me` 返回的权限上下文用于呈现导航和路由门禁。总部权限组、角色和数据范围仍由租户后端决定；门店员工范围仍固定为其所属门店并由服务端再次校验。
- 模块菜单通过 `/api/tenant/v1/modules/menus` 获取；前端不根据许可证缓存自行推断模块开放状态。真实模块 API 继续通过 `ModuleAccessGuard` 判定。
- 已有页面可接入总部模块授权管理；组织、门店和员工 IAM API 可在后续页面增量中接入。不能把导航占位视为这些页面已经交付。
- 门店业务模块页面作为后续模块逐个挂接，当前提供工作区布局和可控路由，不实现会员等业务功能。

## 5. 会话和请求安全

- 平台令牌只保存在平台应用专属存储命名空间；租户令牌/员工主体只保存在租户应用专属命名空间。键名各自前缀化，禁止使用现有旧端 `ec_token`/`ec_user` 键。
- 每个应用有独立 API base URL 配置。开发环境分别代理至 `8081` 和 `8082`；平台控制台部署配置指向平台 API，企业工作台部署配置指向客户自托管的租户 API。部署环境使用显式配置，不在代码中写入环境专属域名或密钥。
- 请求层只附带自身会话令牌；平台响应解析遵从当前 `ApiResponse` contract，租户同理。`401` 清理本应用会话，`403` 保持登录并显示无权状态；网络错误不会伪装成登出。
- 应用启动时通过 `/me` 获取新鲜身份和权限，不把旧 localStorage 主体中的权限当作权威数据。权限或角色变化在下一次 `/me` 或后端请求后生效。
- 路由门禁、导航过滤和按钮可见性只改善交互；任何绕过前端直接请求都必须由后端现有授权规则拒绝。
- 使用不同应用域名/子域名部署时，不共享可访问两个应用的父域 Cookie；本设计不引入跨端 SSO。
- 平台端与客户租户端之间不建立浏览器直连的数据通道。授权同步由客户部署的租户后端按签名协议向平台发起；浏览器使用哪个工作台，就只访问该工作台所属后端。

## 6. 路由与导航契约

- 平台路由使用 `/login`、`/` 和业务域前缀；租户路由使用 `/login`、`/hq/**`、`/store/**`。
- 已登录总部员工访问门店入口时按权限规则拒绝或返回总部入口；门店员工访问总部路径时显示无权页或返回其门店首页，不得仅靠隐藏菜单防护。
- 导航定义包含稳定 key、显示名称、路由、图标标识和所需权限码。所有路径都由同一导航/路由注册信息产生，避免只有菜单受限而直接 URL 可进入。
- 租户动态模块导航使用服务器响应；模块菜单响应缺失、过期或请求失败时 fail closed，不展示可访问的模块路由。
- 错误页明确区分未登录、无权限、资源不存在、后端不可用和空内容；不显示令牌、内部异常栈或敏感请求头。

## 7. 验收标准

1. 两个管理应用分别可独立安装依赖、开发启动、类型检查和生产构建。
2. 平台登录只使用平台 API 与平台令牌；租户登录只使用租户 API 与租户令牌。
3. 一个应用中已有另一个应用的令牌时，不会被附加到请求或被其登出流程删除。
4. 刷新已认证路由后从 `/me` 恢复身份；过期/无效令牌回登录，`403` 保持会话且显示拒绝状态。
5. 平台与租户路由根据最新服务端权限呈现；用户手输无权 URL 仍被前端门禁拒绝，后端仍是最终安全边界。
6. 租户 HQ/STORE 按 `staffType` 进入正确入口；STORE 不会进入 HQ 页面，后端数据范围仍有效。
7. 动态模块菜单来自服务端，未授权或失败时没有模块入口；模块 API 的服务端守卫不能被菜单/路由绕过。
8. 现有 `admin/` 继续通过 TypeScript 与生产构建，现有后端集成测试不回归。
9. 页面不使用伪造经营数据；未接 API 的路由有明确空/未接入状态。

## 8. 部署边界

```text
我们的平台服务器
  ├── 平台总管理端静态资源
  └── platform-app + 平台控制数据库
       ▲
       └── 客户租户后端按授权协议主动发起出站同步/校验

客户企业总部服务器/基础设施
  ├── 企业总部/门店工作台静态资源
  ├── tenant-app
  └── 该企业自己的业务数据库
```

- 平台总管理端登录和 API 只连接平台服务；企业总部/门店工作台登录和 API 只连接该客户自己的租户服务。
- 客户服务器可配置稳定域名或客户认可的网络入口；平台授权校验需要客户租户后端能够按部署文档向平台服务建立出站 HTTPS 连接。
- 企业前端静态资源与租户 API 可由客户通过同域反向代理部署，或按客户基础设施分开部署并配置精确 CORS 来源。平台不要求接管客户企业域名或客户服务器。
- 客户服务器离线时，租户端按已确认的离线授权策略继续工作；恢复联网后由租户后端同步授权。管理端底架不绕过该授权策略。

## 9. 明确不在本子项目内

- 用户侧品牌首页、品牌选择、门店选择、门店快捷入口、网站及小程序品牌化流程。
- 总部经营数据、财务汇总、经营分析、会员等级、订单、支付等尚未具备完整后端契约的业务页。
- API 服务端的角色、权限、数据范围或模块授权规则重写。
- 生产域名、TLS、反向代理、部署流水线或账号密码发放。
- 对 `admin/` 旧页面做批量搬迁或删除。

## 10. 设计自检

- 平台与租户身份隔离贯穿入口、API 客户端、存储与 401 流程。
- 总部/门店共用租户工作台与后端统一租户员工身份契约一致。
- 菜单隐藏不会被描述为安全措施；直接 API 访问仍由服务端控制。
- 品牌客户端和实际业务页面被明确拆出，避免把页面壳误报为阶段完成。
- 两个独立前端的目录名、端口和 API base URL 留由实现计划结合仓库脚本确定；不改变本设计中的应用边界。
- 平台总管理端由平台方托管，企业总部/门店工作台由客户自托管；未把企业业务数据或服务器托管责任转移给平台方。
