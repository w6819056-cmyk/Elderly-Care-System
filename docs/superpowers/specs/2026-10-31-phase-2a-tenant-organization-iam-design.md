# 阶段 2A：企业组织与权限底座设计

日期：2026-10-31  
设计依据：[模块化多企业养老 SaaS 平台设计](2026-10-29-modular-multi-tenant-saas-design.md)  
阶段路线图：[模块化 SaaS 实施路线图](../plans/2026-10-30-modular-saas-delivery-roadmap.md)

## 目标与范围

为单个企业部署的 `tenant-app` 建立可运行的企业组织和员工权限底座：企业本地资料、总部与门店、总部和门店员工账号、企业角色、权限组、角色单独允许/禁止权限，以及总部员工的数据范围。企业管理员可以管理本企业权限，但不能取得或修改平台控制面权限。

本增量不实现客户、服务目录、预约、订单、支付、品牌页、付费模块授权分配和前端工作台；这些由阶段 2B/2C 或后续阶段承接。现有单租户核心链路继续运行，旧接口和 22 项回归测试保持兼容，业务迁移另列阶段 3。

## 部署与数据边界

- 每个企业部署连接其自己的企业业务数据库；平台控制库与企业业务库使用不同数据源和令牌。
- 企业业务库内的 `core_enterprise` 只保存本地企业资料和平台签发的 `org_no`，不保存平台账号、平台角色或平台授权销售明细。
- 所有新增表使用 `core_` 或 `iam_` 前缀，通过租户 Flyway 位置 `classpath:db/migration/tenant` 追加迁移；不修改已存在迁移，不将新表写入带 DROP 的演示 schema。
- 门店停用/撤店由企业总部操作。`SUSPENDED`、`CLOSED` 禁止新经营写入，但总部可查询和导出；生命周期变更不自动释放模块名额，名额规则在 2B 实现。

## 组织模型

`core_enterprise` 在企业数据库内对应唯一企业；`core_store` 保存企业门店。每个门店只能属于当前企业，门店公开编号稳定且唯一。门店状态为 `DRAFT`、`ACTIVE`、`SUSPENDED`、`CLOSED`，只允许显式白名单状态流转。

员工账号存入 `iam_staff`，总部与门店员工均为企业本地身份。总部员工可被分配 `ALL`、`STORE_GROUP`、`STORES`、`SELF` 数据范围；门店员工必须绑定一个门店，其有效范围固定为该门店。请求中的 storeId 仅是筛选条件，服务端必须根据当前员工数据范围重新授权。

## 企业权限模型

- 权限定义由租户程序随模块/API 注册；企业管理员只能组合已注册权限，不能创建任意权限代码。
- `iam_role` 按 `HQ`、`STORE` 限定角色域。
- `iam_permission_group` 是企业可复用权限集合；角色可绑定多个权限组，并设置单独 `ALLOW` / `DENY` 覆盖。
- 有效角色权限 = 权限组权限并集 + 单独允许 - 单独禁止。
- 最终访问还须同时满足员工状态、角色域、数据范围、门店状态和业务对象归属。权限组或角色配置不能扩大员工的数据范围。
- 企业角色及企业令牌不能获得平台权限；平台控制面不读取企业员工或客户表。

## 认证与调用边界

新增企业员工认证入口使用 tenant-app 独立密钥并签发 `TENANT_STAFF` 受众令牌。每次请求通过员工 ID 从当前企业库解析最新账号状态、角色、权限和数据范围，避免把可被撤销的权限长期固化在 JWT 中。旧 `/api/auth/**` 与旧角色令牌暂时兼容，只供现有业务链路使用；新 HQ API 只接受 `TENANT_STAFF` 身份。

总部 API 使用 `/api/tenant/v1/hq/**`，门店员工管理 API 使用 `/api/tenant/v1/store/**`。Controller 负责 HTTP/DTO 校验，应用服务负责编排，仓储负责 SQL。服务层接收显式 `TenantAccessContext`，不从请求参数推断企业身份；跨门店列表必须通过数据范围解析器生成可审计的允许门店集合。

## 错误与审计

使用统一 `ApiResponse` 和稳定错误码：`TOKEN_INVALID`、`PERMISSION_DENIED`、`DATA_SCOPE_DENIED`、`STORE_ACCESS_DENIED`、`STORE_INACTIVE`、`VERSION_CONFLICT`、`BUSINESS_RULE_VIOLATION`、`INTERNAL_ERROR`。敏感字段（密码、令牌、密钥）不进入错误消息或审计详情。门店创建、状态流转、员工创建/停用、角色/权限组修改、角色分配和数据范围变更均记录操作者、目标、动作、traceId 与非敏感变更摘要。

## 验收

1. H2 和 MySQL 8 均能由空库执行新增 Flyway 迁移；生产配置不运行 DROP 初始化。
2. 企业管理员可创建门店、员工、权限组、HQ/STORE 角色并分配权限。
3. 未注册权限被拒；STORE 角色不能绑定总部员工，HQ 角色不能授予门店员工越出本店的范围。
4. 总部 `STORES` 范围只能访问明确分配门店；门店员工无法通过伪造 storeId 访问其他门店。
5. 停用/撤店禁止经营写操作，但总部可读取历史数据；不自动解除模块名额。
6. 新租户令牌不能调用平台 API，平台令牌不能认证为租户员工。
7. 现有 22 项 tenant-app 核心链路测试和全仓架构测试继续通过。
