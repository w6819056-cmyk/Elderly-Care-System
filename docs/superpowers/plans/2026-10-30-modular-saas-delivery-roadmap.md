## 1. 交付目标

把现有单租户养老系统升级为可持续销售和多人协作开发的模块化多企业 SaaS 产品。最终系统由平台控制面、企业租户端、企业品牌客户端三部分组成：

```text
平台运营总端
  └── 管理企业、实例、模块授权、套餐、销售订单、版本和平台审计

企业租户端
  ├── 企业总部端：门店、角色权限、模块名额、品牌、财务汇总、经营分析
  ├── 门店商家端：本店服务、订单、员工、支付、页面和经营数据
  └── 企业业务库：每家企业独立数据库或独立 Schema

企业品牌客户端
  ├── 品牌小程序：品牌首页 -> 选择门店 -> 门店首页 -> 下单支付
  └── 品牌网站：品牌展示、门店直达、微信/支付宝/银联支付适配
```

## 2. 实施原则

1. 采用同一代码仓库、多个可执行程序、模块化单体，不拆微服务。
2. 平台端和租户端分别打包运行，平台令牌和租户令牌完全隔离。
3. 每家企业使用独立业务数据库或独立 Schema，不共享企业业务表。
4. 模块只能通过公开 API 或事件交互，不能直接访问其他模块的 Entity、Mapper 或数据库表。
5. 授权属于企业总部，企业总部再把模块分配给门店；名额按模块分别计算。
6. 平台不保存企业客户、员工、订单、支付、健康等业务数据。
7. 生产环境只使用版本化迁移，禁止依赖 `dev` profile 的 DROP 重建行为。
8. 每个阶段都必须形成可运行、可测试、可评审的软件增量。
9. 每个功能先写失败测试，再写最小实现，测试通过后再重构。
10. 现有 22 个集成测试作为迁移回归基线，必须持续通过。

## 4. 第一条关键路径

首个可执行计划只处理阶段 0 的后端工程基线：

[阶段 0：后端工程基线实施计划](2026-10-30-phase-0-backend-foundation.md)

阶段 0 完成后，关键路径为：

```text
工程基线
  -> 平台认证与企业实例
  -> 模块目录、价格和授权
  -> 企业总部与门店身份权限
  -> 企业业务底座
  -> 现有业务迁移
  -> 机构康养模块
  -> 模块购买与授权闭环
  -> 品牌客户端
```

前端拆分不阻塞平台控制面后端开发。后续单独编写 `admin-platform`、`admin-tenant` 和 `brand-site` 的前端基线计划，避免与后端模块边界同时变化。

## 6. 阶段门禁

每个阶段必须同时满足以下条件才能进入下一阶段：

1. 该阶段新增接口和状态机都有自动化测试。
2. 全仓构建通过，原有回归测试不减少。
3. 无跨模块直接访问 Entity、Mapper 或数据库表。
4. 平台端不依赖企业业务模块实现。
5. 所有数据库变更使用版本化迁移，且已在空库和已有库上验证。
6. 未授权模块在菜单、路由和后端接口三处都被拦截。
7. 日志包含 `traceId`，不输出密码、令牌、支付密钥和健康详情。
8. 文档、接口清单、错误码和迁移说明同步更新。
9. 代码通过评审，接口变更经过负责人确认。
10. 阶段交付物可在干净环境中按文档启动。

## 8. 不做事项

- 不在第一阶段引入微服务、消息中间件集群或 Kubernetes。
- 不支持企业上传任意 Java 包、脚本或动态插件。
- 不把全部企业业务数据集中到平台控制库。
- 不在阶段 0 实现完整业务模块，只建立可验证的工程和契约基线。
- 不在生产环境启用 `spring.sql.init` 的 DROP 重建行为。
- 不用未经脱敏的生产数据做开发和演示。
